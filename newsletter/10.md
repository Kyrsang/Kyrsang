
ANTLR로 구축하는 SQL 정적 분석 엔진 — 전사 규모 레거시 SQL을 구조적으로 이해하는 방법

안녕하세요, AMO 이은상입니다.

최근 전사 현업 부서들로부터 취합한 4,000여 개의 레거시 SQL 파일을 분석해야 하는 업무를 마주했습니다. 수천 개 파일 단위로 분산된 쿼리를 사람이 직접 검토하는 방식은 한계가 명확했기에, 코드베이스 전체를 하나의 데이터셋으로 구조화하여 정적 분석을 수행하는 애플리케이션을 개발하게 되었습니다. 이번 뉴스레터에서는 해당 애플리케이션에 활용된 근간 기술인 오픈소스 ANTLR의 기본적인 동작 방식과 그 활용을 알아보도록 하겠습니다.

## 1. Lexer와 Parser 

쿼리를 직접 실행하는 DB2 엔진이 아닌 이상, 외부 프로그램의 관점에서 SQL 파일은 그저 의미가 배제된 연속된 문자열에 불과합니다. 이 거대한 텍스트 집합을 프로그램이 이해하고 적절한 행위를 수행하도록 만들려면, 먼저 DB2 SQL 규격과 문법에 맞게 구성되었는지 확인하는 과정이 필요합니다. 가장 단순한 예로 `SELECT * FROM table1, table2`라는 문장에서 `FROM` 절의 테이블 목록만 추출하는 상황을 생각해 보겠습니다. 정규식을 이용한 텍스트 패턴 매칭으로도 간단한 조회는 가능해 보이지만, 주석의 개입, 불규칙한 공백, 중첩된 서브쿼리나 복잡한 조인 조건이 얽히기 시작하면 순식간에 그 한계를 드러냅니다.

ANTLR는 이 문제를 해결하기 위해 문자를 다루는 단계를 어휘 분석(Lexer)과 구문 분석(Parser)으로 나눕니다. Lexer는 쿼리 텍스트 전체에서 공백과 주석 등 구문 해석과 관련 없는 요소를 정리하고, 연속된 문자열을 키워드·식별자·연산자 등의 의미 단위인 토큰(Token) 배열로 변환합니다. 이어지는 Parser는 문자의 위치나 공백 같은 하위 레이어의 제어 로직에서 벗어나, 정제된 토큰 배열의 순서를 검사하고 문법 규칙에 따라 구문 트리(Abstract Syntax Tree, 이하 AST)[1]로 조립하는 역할에만 집중하게 됩니다.

ANTLR는 이러한 처리 규칙을 .g4라는 단일 문법 정의 파일 안에서 기술합니다. 대문자로 기술하는 Lexer 규칙으로 토큰의 형태로 자를 단위를 정의하고, 소문자로 기술하는 Parser 규칙으로 토큰들이 어떤 순서로 결합하여 하나의 문장 구조를 이루는지 표현하는 식입니다. 기초적인 SQL문 분석을 위한 ANTLR 문법 정의 예시는 다음과 같습니다. 예시 코드에서 활용될 문법의 이름을 `SimpleSql`이라고 칭하겠습니다. 

```antlr
grammar SimpleSql;

// Parser (문장 구조) 
statement
    : SELECT selectList FROM tableList EOF
    ;

selectList
    : STAR
    | IDENTIFIER (COMMA IDENTIFIER)*
    ;

tableList
    : IDENTIFIER (COMMA IDENTIFIER)*
    ;

// Lexer (단어 단위)
SELECT     : [Ss][Ee][Ll][Ee][Cc][Tt];
FROM       : [Ff][Rr][Oo][Mm];
STAR       : '*';
COMMA      : ',';
IDENTIFIER : [a-zA-Z_][a-zA-Z_0-9]*;
WS         : [ \t\r\n]+ -> skip;
```
> .g4 파일 작성 문법
>
> * 선택 (`|`): `STAR`(`*`) 또는 `IDENTIFIER` 중 하나가 위치함을 의미 
> * 반복 (`()*`): 정규식 표기법과 동일하게, 쉼표로 구분된 구문이 0회 이상 반복될 수 있음을 표현 
> * 대소문자 허용 (`[Ss][Ee]...`): 대소문자 구분 없이 키워드를 인식 (e.g. `SELECT`, `select`, `SeLeCt`, ..)
> * 동작 제어 (`-> skip`): 공백(`WS`) 등 구문 분석에 불필요한 토큰을 제외

ANTLR CLI로 문법 파일을 컴파일하면, 선언된 규칙을 그대로 구현한 파이썬 모듈들이 자동으로 생성됩니다. 소스코드 분석을 위한 어휘 분석기(Lexer)와 구문 파서(Parser)가 실행 가능한 코드의 형태로 준비되는 것입니다. 

생성된 모듈을 애플리케이션 로직에서 활용하는 예시는 아래와 같습니다. 

```python
from antlr4 import InputStream, CommonTokenStream
from SimpleSqlLexer import SimpleSqlLexer
from SimpleSqlParser import SimpleSqlParser

sql = "SELECT * FROM table1, table2"

lexer = SimpleSqlLexer(InputStream(sql))
tokens = CommonTokenStream(lexer)
parser = SimpleSqlParser(tokens)
tree = parser.statement()
```

이처럼 간단한 객체 참조만으로 SQL 분석이 가능해지는 이유는, ANTLR가 생성한 파이썬 코드(예: `SimpleSqlParser.py`) 내부에 `SimpleSql` 문법 규칙이 1:1로 대응하는 명시적인 제어 흐름(Control Flow) 코드로 구현되어 있기 때문입니다. 

`SimpleSqlParser.py` 코드 중 `statement()` 메소드를 예시로 살펴보겠습니다.  

```python
def statement(self):
    # ... 
    self.match(SimpleSqlParser.SELECT)
    self.selectList()
    self.match(SimpleSqlParser.FROM)
    self.tableList()
    self.match(SimpleSqlParser.EOF)
    # ... 
```

파서는 앞서 정의한 `SimpleSql` 문법에 따라 토큰을 순차적으로 검사하고 하위 규칙의 메서드(`selectList`, `tableList`)를 순서대로 호출합니다. 개발자가 수동으로 작성하던 복잡한 분기문과 재귀 함수 호출을, 자동 생성된 코드가 대신 처리해 주고 있는 것입니다. 

이러한 실행 과정을 거쳐 평면적인 텍스트 쿼리가 메모리상 부모-자식 관계를 가지는 계층적인 AST로 재구성되면, 애플리케이션은 AST를 출력해보거나 노드를 직접 탐색하는 것만으로 필요한 메타데이터를 즉시 추출할 수 있게 됩니다.

```python
print(tree.toStringTree(recog=parser))
# Output: (statement SELECT (selectList *) FROM (tableList table1 , table2) <EOF>)

tables = [t.getText() for t in tree.tableList().IDENTIFIER()]
print(tables)
# Output: ['table1', 'table2']
```
> 파이썬 애플리케이션 런타임 환경에서 SQL의 AST를 탐색해 참조된 테이블 명(`table1`, `table2`)을 추출한 모습


## 2. Visitor 패턴 — 컬럼이 어느 테이블에 속하는지 추적하기

이제 단순한 테이블 식별을 넘어, `u.user_id`처럼 별칭이 부여된 컬럼이 실제로 어느 테이블에 속하는지 명확히 추적해 보겠습니다.

분석 대상이 될 예시 쿼리는 다음과 같습니다.
```sql
SELECT u.user_id, o.order_id
FROM users AS u
JOIN orders AS o ON u.user_id = o.user_id
```

이러한 쿼리를 해석하려면 JOIN 절과 Table Alias, 그리고 (`.`) 구분자를 인식할 수 있는 확장된 파서 규칙이 필요합니다.
기존 `SimpleSql`을 한 단계 발전시킨 `AdvancedSql` 문법 정의는 다음과 같습니다.

```antlr
grammar AdvancedSql;

// Parser (문장 구조) 
statement
    : SELECT selectList FROM tableRef joinPart* EOF  // 변경: tableList => tableRef, 추가: joinPart* 
    ;

selectList
    : STAR
    | column (COMMA column)*  // 변경: IDENTIFIER 대신 column 파서 규칙 적용
    ;

// 추가: 별칭 접두어와 컬럼명을 분리하여 인식하는 컬럼 구문 정의 
column
    : (qualifier=IDENTIFIER DOT)? name=IDENTIFIER
    ;

// 추가: 테이블 및 Alias 정의
tableRef
    : name=IDENTIFIER (AS? alias=IDENTIFIER)?
    ;

// 추가: JOIN 절 구성
joinPart
    : JOIN tableRef ON joinCondition
    ;

// 추가: JOIN 조건식 
joinCondition
    : left=column EQ right=column
    ;

// Lexer (단어 단위)
SELECT : [Ss][Ee][Ll][Ee][Cc][Tt];
FROM   : [Ff][Rr][Oo][Mm];
JOIN   : [Jj][Oo][Ii][Nn];  // 추가
ON     : [Oo][Nn];          // 추가
AS     : [Aa][Ss];          // 추가
STAR   : '*';
COMMA  : ',';
DOT    : '.';               // 추가
EQ     : '=';               // 추가
IDENTIFIER : [a-zA-Z_][a-zA-Z_0-9]*;
WS     : [ \t\r\n]+ -> skip;

```
> * 라벨링 (`label=rule`): `qualifier=IDENTIFIER`처럼 이름을 부여하여, 생성된 코드(Python 등)에서 `ctx.qualifier`와 같이 해당 요소에 바로 접근할 수 있도록 지정
> * `column` 파서 정의: `(qualifier=IDENTIFIER DOT)?`를 통해 `a.acct_id` 형태의 테이블 별칭(Alias) 접두어 구성을 선택적으로 수용하도록 표현
> * 옵셔널 (`?`): `AS?`와 같이 별칭 키워드 등이 생략되거나 1회 등장할 수 있음을 표현

이렇게 문법 규칙을 확장하고 나면 AST의 구조가 한층 복잡해집니다. `column` 규칙만 하더라도 SELECT 절뿐만 아니라 JOIN의 ON 절처럼 AST의 전혀 다른 위치에서 동적으로 등장하기 때문입니다. 

ANTLR의 Visitor 패턴은 이처럼 복잡해진 AST 순회 작업을 개발자가 쉽게 다룰 수 있도록 Visitor 개념으로 추상화하여 제공합니다. 전체 AST를 탐색하는 순서는 베이스 클래스(`AdvancedSqlVisitor.py`)가 내부적으로 처리하므로, 우리는 테이블 식별이나 컬럼 추출이 필요한 시점에 `visitTableRef`, `visitColumn`과 같은 추상화된 메서드를 통해 원하는 행위를 정의하기만 하면 됩니다.

이렇게 추상화된 메서드들을 활용하면, AST에서 컬럼의 실제 원천 테이블을 추적하는 로직을 두 단계의 탐색 과정으로 구현할 수 있습니다. 첫 번째 탐색에서 Alias와 테이블명의 매핑 정보(`alias_map`)를 먼저 구한 뒤, 두 번째 탐색에서 `column` 노드를 만날 때마다 이 매핑을 참조해 소속 테이블을 매칭하는 구조입니다.

```python
class TableRefVisitor(AdvancedSqlVisitor):
    """First pass: build alias -> real table name."""

    def __init__(self):
        self.alias_map = {}

    def visitTableRef(self, ctx):
        table = ctx.name.text.upper()
        alias = ctx.alias.text.upper() if ctx.alias else table
        self.alias_map[alias] = table
        return self.visitChildren(ctx)

class ColumnVisitor(AdvancedSqlVisitor):
    """Second pass: resolve every column reference through that map."""

    def __init__(self, alias_map):
        self.alias_map = alias_map
        self.columns = []

    def visitColumn(self, ctx):
        table = (
            self.alias_map.get(ctx.qualifier.text.upper())
            if ctx.qualifier
            else None
        )
        self.columns.append((table, ctx.name.text.upper()))
        return self.visitChildren(ctx)
```

아래 쿼리를 대상으로 탐색을 수행하면 AST로부터 다음과 같은 최종 매핑 결과가 산출됩니다.

```python
sql = "SELECT u.user_id, o.order_id FROM users AS u JOIN orders AS o ON u.user_id = o.user_id"

# 1단계: TableRefVisitor 수행 결과
# alias_map = {'U': 'USERS', 'O': 'ORDERS'}

# 2단계: ColumnVisitor 수행 결과
# columns   = [
#     ('USERS', 'USER_ID'),
#     ('ORDERS', 'ORDER_ID'),
#     ('USERS', 'USER_ID'),
#     ('ORDERS', 'USER_ID')
# ]
```

다만, 실제 복잡한 레거시 SQL을 다룰 때는 이것만으로 부족할 수 있습니다. 한정되지 않은 컬럼의 원천을 정확히 찾아내려면 서브쿼리나 CTE의 스코프 영역을 따로 관리하고, DB 메타데이터 정보까지 결합하는 한 단계 더 깊은 의미 분석이 필요해집니다.

3. 실전 프로덕션 환경 적용기 — metchurial

앞서 살핀 파싱 기법을 확장하여, 쿼리 파싱 엔진 `metchurial`을 커맨드 라인 애플리케이션 형태로 개발하여 전사 현업 부서로부터 제공받은 4,000여 개의 .sql 파일을 스캔하고 정적 분석해 보았습니다.

스캔 과정에서 확인된 인상적인 점은, 이 방대한 쿼리들 상당수가 완전히 이질적인 구조가 아니라 오랜 세월 동안 변화하는 비즈니스 요건에 유연하게 대응하는 과정에서 별칭이나 일부 컬럼이 점진적으로 분기되어 온 파생형들이라는 사실이었습니다. 동일 쿼리의 판단 기준을 세분화함에 따라 17,000개의 문장은 5,000개 또는 10,000개의 핵심 쿼리로 식별할 수 있었습니다.

이러한 정제 결과를 얻기까지 `metchurial` 개발 과정에서 가장 깊이 고민한 지점은, 실제 현업 환경의 불완전한 SQL 파일들에서 발생하는 에지 케이스들을 얼마나 유연하게 처리할 수 있는가였습니다.

### DB2 ANTLR 문법의 조인 구문 수정 

실제 현업에서 사용되는 쿼리를 정적 분석함에 있어 발생하였던 수많은 에지 케이스 중에서도 가장 까다로웠던 형태는, ANTLR GitHub 공식 리포지토리 `grammars-v4`에서 관리되는 IBM DB2 SQL 문법(`sql/db2/Db2Parser.g4`, `sql/db2/Db2Lexer.g4`) 상 일부 정의가 누락되어 분석 결과로 생성되는 AST가 온전히 쿼리를 분석하지 못하는 경우였습니다. 가장 대표적인 사례가 아래와 같은 ANSI JOIN 구문이었습니다.

```sql
SELECT * FROM TBACCT A JOIN TBCTRT B ON A.id = B.id;
```

해당 쿼리는 에러 없이 파싱되지만, AST에서 조인 노드가 누락되는 현상이 있었습니다. 원인을 추적해 보니 파서 내부의 조인 정의는 존재하나, 순환 참조로 인한 파서 빌드 오류를 피하려고 상위 규칙과의 연결이 주석 처리된 상태였습니다. 이를 해결하기 위해 복잡한 우회 경로를 정리하고 테이블 참조 규칙에서 조인을 직접 처리하도록 문법을 단순화했습니다. (해당 수정안은 원본 오픈소스 리포지토리에도 PR을 제출하여 리뷰를 기다리는 중입니다.)

### 한글 문자 파싱 문제 

두 번째 문제는 한글 식별자 파싱 문제였습니다. 정적 분석 간, 다수의 문법상 문제없는 SQL 파일들이 분석에 실패하는 점을 확인하였는데, 원인은 아래와 같은 한글 별칭(Alias)이었습니다.

```sql
SELECT column1 가나다, a.column2 라마바
FROM tbl_a 
```
레거시 DB2 환경에서는 한글 별칭이 흔히 쓰이지만, 원본 DB2 ANTLR 문법의 식별자(ID) 규칙은 아스키(ASCII) 문자만 허용하도록 정의되어 있어, 한글 별칭을 만나는 순간 문법 에러가 발생한 것이었습니다. 해결책은 식별자 규칙에 유니코드 한글 범위(`가-힣`)를 추가하여 한글 별칭도 유효한 토큰으로 파싱되도록 문법을 수정하는 것이었습니다.

## 4. 마치며

ANTLR를 활용한 애플리케이션을 통해 수천 개에 달하는 레거시 SQL을 다루면서, 텍스트 형태의 쿼리를 구조화하여 분석하는 방법의 유용함을 경험할 수 있었습니다.

정규식만으로는 한계가 명확했던 파싱 작업을 ANTLR를 통해 해결해 나가면서, 흩어져 있던 쿼리들의 메타데이터와 관계를 조금 더 명확하게 파악하게 되었습니다. 복잡한 레거시 쿼리 집합을 체계적으로 정리해 볼 수 있었던 의미 있는 경험이었습니다.

긴 글 읽어주셔서 감사드립니다.

이은상 드림

[1] AST: ANTLR가 구문 분석 직후 출력하는 결과물은 파싱 과정을 있는 그대로 표현한 CST(Concrete Syntax Tree)입니다. 하지만 본 글에서는 문맥 해석과 메타데이터 추출이라는 목적에 집중하기 위해, 용어를 AST(Abstract Syntax Tree, 신택스 트리)로 통일하여 기술하였습니다.
