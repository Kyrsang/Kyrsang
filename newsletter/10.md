최근 현업 부서들로부터 전달받은 4,000여 개의 레거시 SQL 파일을 분석해야 하는 업무를 마주했습니다. 수천 개 파일 단위로 분산된 쿼리를 사람이 직접 검토하는 방식은 한계가 명확했기에, 코드베이스 전체를 하나의 데이터셋으로 구조화하여 정적 분석을 수행하는 애플리케이션을 개발하게 되었습니다. 이번 뉴스레터에서는 해당 애플리케이션에 활용된 근간 기술인 오픈소스 ANTLR의 기본적인 동작 방식과 그 활용을 알아보도록 하겠습니다.

1. Lexer와 Parser 

쿼리를 직접 실행하는 DB2 엔진이 아닌 이상, 외부 프로그램의 관점에서 SQL 파일은 그저 의미가 배제된 연속된 문자열에 불과합니다. 이 거대한 텍스트 집합을 프로그램이 이해하고 적절한 행위를 수행하도록 만들려면, 먼저 DB2 SQL 규격과 문법에 맞게 구성되었는지 확인하는 과정이 필요합니다. 가장 단순한 예로 `SELECT * FROM table1, table2`라는 문장에서 `FROM` 절의 테이블 목록만 추출하는 상황을 생각해 보겠습니다. 정규식을 이용한 텍스트 패턴 매칭으로도 간단한 조회는 가능해 보이지만, 주석의 개입, 불규칙한 공백, 중첩된 서브쿼리나 복잡한 조인 조건이 얽히기 시작하면 순식간에 그 한계를 드러냅니다.

ANTLR는 이 문제를 해결하기 위해 문자를 다루는 단계를 어휘 분석(Lexer)과 구문 분석(Parser)으로 나눕니다. Lexer는 쿼리 텍스트 전체에서 공백과 주석 등 구문 해석과 관련 없는 요소를 정리하고, 연속된 문자열을 키워드·식별자·연산자 등의 의미 단위인 토큰(Token) 배열로 변환합니다. 이어지는 Parser는 문자의 위치나 공백 같은 하위 레이어의 제어 로직에서 벗어나, 정제된 토큰 배열의 순서를 검사하고 문법 규칙에 따라 구문 트리(Abstract Syntax Tree, AST)로 조립하는 역할에만 집중하게 됩니다.

ANTLR는 이러한 처리 규칙을 .g4라는 단일 문법 정의 파일 안에서 기술합니다. 대문자로 기술하는 Lexer 규칙으로 토큰의 형태로 자를 단위를 정의하고, 소문자로 기술하는 Parser 규칙으로 토큰들이 어떤 순서로 결합하여 하나의 문장 구조를 이루는지 표현하는 식입니다. 기초적인 SQL문 분석을 위한 ANTLR 문법 정의 예시는 다음과 같습니다. 예시 코드에서 활용될 문법의 이름을 `SimpleSql`이라고 칭하겠습니다. 

```antlr
grammar SimpleSql;

// Parser (문장 구조) 
statement
    : SELECT selectList FROM tableList EOF
    ;

selectList
    : STAR
    | IDENTIFIER (COMMA IDENTIFIER)*
    ;

tableList
    : IDENTIFIER (COMMA IDENTIFIER)*
    ;

// Lexer (단어 단위)
SELECT     : [Ss][Ee][Ll][Ee][Cc][Tt];
FROM       : [Ff][Rr][Oo][Mm];
STAR       : '*';
COMMA      : ',';
IDENTIFIER : [a-zA-Z_][a-zA-Z_0-9]*;
WS         : [ \t\r\n]+ -> skip;
```
> .g4 파일 작성 문법
>
> * 선택 (`|`): `STAR`(`*`) 또는 `IDENTIFIER` 중 하나가 위치함을 의미합니다.
> * 반복 (`()*`): 정규식 표기법과 동일하게, 쉼표로 구분된 구문이 0회 이상 반복될 수 있음을 표현합니다.
> * 동작 제어 (`-> skip`): 공백(`WS`) 등 구문 분석에 불필요한 토큰을 제외하라는 지시어입니다.

ANTLR CLI로 문법 파일을 컴파일하면, 선언된 규칙을 그대로 구현한 파이썬 모듈들이 자동으로 생성됩니다. 소스코드 분석을 위한 어휘 분석기(Lexer)와 구문 파서(Parser)가 실행 가능한 코드의 형태로 준비되는 것입니다. 

생성된 모듈을 애플리케이션 로직에서 활용하는 예시는 아래와 같습니다. 

```python
from antlr4 import InputStream, CommonTokenStream
from SimpleSqlLexer import SimpleSqlLexer
from SimpleSqlParser import SimpleSqlParser

sql = "SELECT * FROM table1, table2"

lexer = SimpleSqlLexer(InputStream(sql))
tokens = CommonTokenStream(lexer)
parser = SimpleSqlParser(tokens)
tree = parser.statement()
```

이처럼 간단한 객체 참조만으로 SQL 분석이 가능해지는 이유는, ANTLR가 생성한 파이썬 코드(예: `SimpleSqlParser.py`) 내부에 `SimpleSql` 문법 규칙이 1:1로 대응하는 명시적인 제어 흐름(Control Flow) 코드로 구현되어 있기 때문입니다. 

`SimpleSqlParser.py` 코드 중 `statement()` 메소드를 예시로 살펴보겠습니다.  

```python
def statement(self):
    # ... 
    self.match(SimpleSqlParser.SELECT)
    self.selectList()
    self.match(SimpleSqlParser.FROM)
    self.tableList()
    self.match(SimpleSqlParser.EOF)
    # ... 
```

파서는 앞서 정의한 `SimpleSql` 문법에 따라 토큰을 순차적으로 검사하고 하위 규칙의 메서드(`selectList`, `tableList`)를 순서대로 호출합니다. 개발자가 수동으로 작성하던 복잡한 분기문과 재귀 함수 호출을, 자동 생성된 코드가 대신 처리해 주고 있는 것입니다. 

이러한 실행 과정을 거쳐 평면적인 텍스트 쿼리가 메모리상 부모-자식 관계를 가지는 계층적인 객체 트리로 재구성되면, 애플리케이션은 트리를 출력해보거나 노드를 직접 탐색하는 것만으로 필요한 메타데이터를 즉시 추출할 수 있게 됩니다.

```python
print(tree.toStringTree(recog=parser))
# Output: (statement SELECT (selectList *) FROM (tableList table1 , table2) <EOF>)

tables = [t.getText() for t in tree.tableList().IDENTIFIER()]
print(tables)
# Output: ['table1', 'table2']
```

2. Visitor 패턴 — 컬럼이 어느 테이블에 속하는지 추적하기

이제 한 단계 더 나아가 봅시다. 단순 테이블 추출을 넘어 `a.acct_id`처럼 테이블 별칭(Alias)이 붙은 상황에서 각 컬럼이 실제로 어느 테이블 소속인지 정확히 찾아내고 싶습니다.

이를 위해 문법 규칙도 확장해 줍니다. JOIN, ON, Alias, 그리고 점(`.`)으로 연결된 컬럼 참조를 표현할 수 있도록 파서 규칙을 추가합니다. 이해를 돕기 위해 WHERE 조건절은 제외했지만, 복잡도의 본질은 조건식 유무가 아니라 컬럼이라는 토큰이 여러 규칙에 걸쳐 등장한다는 점에 있습니다.

```antlr
statement
    : SELECT selectList FROM tableRef joinPart* EOF
    ;

column
    : (qualifier=IDENTIFIER DOT)? name=IDENTIFIER
    ;

tableRef
    : name=IDENTIFIER (AS? alias=IDENTIFIER)?
    ;

joinPart
    : JOIN tableRef ON joinCondition
    ;

joinCondition
    : left=column EQ right=column
    ;

```

이 시점부터 단순 노드 탐색 방식은 한계를 만납니다. `column` 규칙은 이제 SELECT 절 내부뿐만 아니라 JOIN의 ON 절 등 트리 곳곳에 등장합니다. 트리의 어디서 몇 번 나타날지 알 수 없는 노드들을 일일이 하드코딩하는 방식은, 규칙이 복잡해질수록 재귀 탐색 코드가 기하급수적으로 늘어나는 결과를 초래합니다.

ANTLR가 `-visitor` 옵션으로 함께 생성해 주는 Visitor 베이스 클래스는 이 트리 순회 작업을 깔끔하게 추상화해 줍니다. 관심 있는 노드 타입만 `visitXxx` 메서드로 오버라이드하고, 나머지는 `visitChildren`에 맡기면 트리 전체를 빠짐없이 자동 순회합니다.

컬럼과 실제 테이블을 매핑하려면 2단계 순회 과정이 필요합니다. 먼저 `tableRef`를 순회하며 테이블 Alias 대응표(`alias_map`)를 구축한 뒤, `column`을 순회하며 앞서 만든 대응표를 참조해 컬럼의 실제 소속 테이블을 구체화하는 방식입니다.

```python
class TableRefVisitor(AdvancedSqlVisitor):
    def __init__(self):
        self.alias_map = {}

    def visitTableRef(self, ctx):
        table = ctx.name.text.upper()
        alias = ctx.alias.text.upper() if ctx.alias else table
        self.alias_map[alias] = table
        return self.visitChildren(ctx)


class ColumnVisitor(AdvancedSqlVisitor):
    def __init__(self, alias_map):
        self.alias_map = alias_map
        self.columns = []

    def visitColumn(self, ctx):
        table = self.alias_map.get(ctx.qualifier.text.upper()) if ctx.qualifier else None
        self.columns.append((table, ctx.name.text.upper()))
        return self.visitChildren(ctx)

```

`SELECT a.acct_id, b.ctrt_no, stat_cd FROM tbacct AS a JOIN tbctrt AS b ON a.acct_id = b.acct_id` 구문을 입력하면 `alias_map`은 `{'A': 'TBACCT', 'B': 'TBCTRT'}`로 구축되며, `columns`는 `[('TBACCT', 'ACCT_ID'), ('TBCTRT', 'CTRT_NO'), (None, 'STAT_CD'), ('TBACCT', 'ACCT_ID'), ('TBCTRT', 'ACCT_ID')]`라는 결과를 내놓습니다.

여기서 세 번째 항목에 주목해 볼 필요가 있습니다. SELECT 절에 Alias 없이 사용된 `stat_cd`는 단순 문법 규칙만으로는 소속 테이블을 확정할 수 없어 `None`으로 남습니다. 실제로 복잡한 DB2 SQL을 정적 분석할 때도 동일한 한계에 부딪히게 됩니다. 한정되지 않은 컬럼은 단순 Alias 매핑을 넘어, 해당 컬럼이 위치한 정확한 스코프(서브쿼리, CTE 등)까지 정밀하게 추적해야 비로소 해결됩니다.


3. 실전 프로덕션 환경 — 4천 개 SQL 파일이 던진 엔지니어링 과제들

metchurial은 이 파싱 기법을 IBM Db2 LUW SQL 오픈소스 문법에 적용하여 실제 프로덕션 수준으로 끌어올린 결과물입니다.

실제 업무 환경에서 4,000여 개의 .sql 파일을 스캔한 결과, 총 17,000여 개의 개별 쿼리 문장으로 분해되었습니다. 흥미로운 점은 이 수만 개의 쿼리 중 상당수가 완전히 새로운 쿼리가 아니라, 오랜 세월에 걸쳐 Alias나 일부 컬럼만 살짝 바뀐 복사-붙여넣기 변형이었다는 사실입니다.

동일 쿼리의 판단 기준을 테이블 및 JOIN 구조로 볼 것인지, 아니면 WHERE 조건식까지 포함할 것인지에 따라 17,000개 문장은 각각 5,000개 및 10,000개의 유일한 핵심 쿼리 그룹(Core Query Identity)으로 압축되었습니다. 이러한 성과를 거두기까지 실전 대규모 스캔 환경에서 발생했던 엔지니어링 이슈와 최적화 경험을 공유합니다.

예측 모드(Prediction Mode)와 에러 전략 튜닝 측면에서는 WHERE 절에 수만 개의 리터럴이 나열된 `IN (...)` 형태의 쿼리를 다루는 것이 과제였습니다. ANTLR의 기본 예측 알고리즘은 토큰 하나마다 과도한 연산을 수행하며 파싱을 수 시간 동안 지연시키는 병목을 일으킵니다. 이를 해결하기 위해 예측 모드를 SLL(`PredictionMode.SLL`)로 전환하여 문법적 모호성이 없는 구간에서 속도를 획기적으로 향상시켰습니다. 또한 `BailErrorStrategy`를 적용하여 구문 오류 발생 시 복구 연산을 건너뛰고 예외를 즉시 발생시켜 애플리케이션의 재동기화 로직으로 제어권을 빠르게 넘기도록 설계했습니다.

파싱 작업의 멀티 프로세싱 병렬화도 필수적이었습니다. SQL 파싱은 전형적인 CPU-bound 연산이므로 Python 단일 프로세스 환경에서는 GIL(Global Interpreter Lock)로 인해 멀티 스레딩의 효과를 볼 수 없습니다. 각 SQL 파일이 서로 완전히 독립적이라는 특성을 활용해 `ProcessPoolExecutor` 기반의 멀티 프로세스 스캔을 적용했으며, 그 결과 CPU 코어 수에 비례하는 스캔 속도 향상을 얻었습니다.

훼손된 파일 방어 및 자동 격리(Quarantine) 체계 역시 마련했습니다. 실무 코드베이스에는 구분선(`========`), 한글 제목 주석, 혹은 작성 중 잘린 쿼리 등 비표준 파일들이 다수 존재합니다. 파싱을 시도하기 전 토큰 스트림 레벨에서 연속된 특수문자나 렉서 에러 비율을 미리 감지하고, 이상 파일은 `_quarantine/bad_files/` 폴더로 물리적 이동 조치하여 전체 스캔 프로세스의 안정성을 확보했습니다.

마지막으로 파스 트리 기반 쿼리 지문(Identity) 생성을 통해 수만 개의 SQL 중 구조적으로 동일한 쿼리를 식별했습니다.

```python
import hashlib

def core_id(sql: str) -> str:
    tree = parse(sql)
    facts = build_facts(tree)  # 예: {"TBL|TBACCT", "REL|TBACCT|TBCTRT", ...}
    signature = "\n".join(sorted(facts))
    return hashlib.sha256(signature.encode()).hexdigest()[:16]

q1 = "SELECT a.acct_id, b.ctrt_no FROM tbacct AS a JOIN tbctrt AS b ON a.acct_id = b.acct_id"
q2 = "SELECT x.acct_id, x.acct_nm, y.ctrt_no FROM tbacct AS x JOIN tbctrt AS y ON x.acct_id = y.acct_id"
q3 = "SELECT a.acct_id FROM tbacct AS a JOIN tbstat AS s ON a.acct_id = s.acct_id"

# core_id(q1) == core_id(q2)  -- Alias와 SELECT 절이 달라도 동일한 구조를 가지므로 같은 쿼리로 식별
# core_id(q1) != core_id(q3)  -- 참여하는 테이블이 다르면 서로 다른 쿼리로 식별

```

`q1`과 `q2`는 Alias와 SELECT 항목이 완전히 다르지만, 동일한 두 테이블을 같은 조건으로 JOIN하고 있어 동일한 `core_id`로 그룹핑됩니다. 반면 `q3`는 결합된 테이블이 다르므로 별개의 `core_id`가 부여됩니다. 이 Fact 집합에 WHERE 조건절까지 포함하느냐에 따라 식별 기준이 유연하게 달라지며, 이를 통해 17,000개의 문장을 5,000개 혹은 10,000개의 유의미한 그룹으로 정제할 수 있었습니다.


4. 마치며

이번 프로젝트를 진행하며 SQL 텍스트는 문법 구조를 통과하기 전까지 그저 무의미한 문자열에 불과하다는 점을 다시금 체감했습니다.

Lexer는 문자열을 토큰으로 자르고, Parser는 토큰을 파스 트리로 구성하며, Visitor는 파스 트리를 우리가 원하는 구조화된 데이터로 변환합니다. 이 세 계층의 조합은 테이블 이름 하나를 뽑아내는 가장 단순한 예제부터 4,000개 파일 속 17,000개 문장을 분석해 5,000여 개의 유익한 쿼리 그룹을 찾아내는 대규모 정적 분석 환경까지 동일한 원리로 작용합니다. 다만 데이터의 규모가 커질수록 문법 자체의 작성보다 문법을 얼마나 빠르고 안전하게 대량으로 적용할 것인가라는 엔지니어링적 최적화가 더욱 큰 비중을 차지하게 됩니다.
